## 一、原版逐帧拆解

| 阶段 | 时长 | 表现 |
|------|------|------|
| **触发** | — | 长按屏幕上的文字（或双指按压） |
| **前摇** | ~120ms | 屏幕轻微内缩（0.96）、背景压暗、轻微震动 |
| **判定** | ~200ms | 把当前屏幕文字切成"语义块" |
| **炸开** | ~220ms | 文字块从原位飞散到网格，块间留缝 |
| **操作** | — | 点选/划选 / 顶栏：复制·搜索·词典·切开·分享（OS 8 实机确认） |
| **收招** | ~180ms | 词块飞回原位，背景恢复 |

> **R2 实机修正（2026-11-14）**：
> - 顶栏真实动作 = 复制 · 搜索 · 词典 · **切开** · 分享；「切开」= 逐字分词
>   （选中的词块重新切成单字块，`second_boom`，粒度二档切换）
> - ~~长按拖动词块合并~~ 不存在，老文档想当然了
> - 长文分段：上拉炸下一段 / 下拉炸上一段（`top/bottom_warning` 字符串）

**关键手感**：不是"弹出面板"，是"把屏幕上的字抖散再拼回去"。
所以动效的起点必须是**原文字的真实位置**，不能是从屏幕中间飞出来。

## 二、触发：拇指压上去就炸

**能做到。用 Shizuku 以 shell 身份直读触摸设备的事件流，不走系统长按信号。**

> 旧结论已作废：曾打算「等系统先进入选词，再抢过来炸」。这条路会与备忘录点选、微信菜单抢手势，
> 实机验证用户明确否决。原版锤子是 framework 级长按替换，第三方只能从输入层做。

```
用户拇指按住文字
  → Shizuku 读 /dev/input/event7 的 evdev 二进制事件（24 字节固定帧）
  → 按下 + 位移在阈值内 + 持续 ≥ 360ms
  → 查无障碍树：手指下面那个节点有字？
       有 → 炸该节点全文
       没有 → 静默，系统长按照常
```

实机（Meizu 21 Pro / Android 16）：触摸设备 `main_touch`，原始坐标 13680×31920。
从按住到面板出现实测 < 400ms。

`input motionevent UP` 注入在这台机器**取消不了原 App 的长按菜单**——注入走虚拟输入设备，
和真实触摸不是同一条流。所以「顶掉系统菜单」这一步当前做不到，面板直接盖上去。


### 为什么不能自己判断"按住 400ms"

安卓 14 有两个 API 能拿到全局触摸，两条都不能用：

| API | 为什么不行 |
|---|---|
| `AccessibilityService.onMotionEvent` | **独占**。一旦监听触摸屏，事件不再发给 App。短按、滑动、长按全部失效——等于自己重写一套输入系统，每个点击都要延迟判断再转发，整台手机变得黏手 |
| `setObservedMotionEventSources` | 旁路监听，但它是 `@hide` 隐藏 API + 实验 flag，魅族上大概率不存在 |

**结论：只能"接信号"，不能"抢信号"。** 这是安卓给第三方的唯一通道。

### 覆盖范围

| 场景 | 压一下就炸？ |
|---|---|
| 微信 / QQ 聊天消息 | 能（要验证发的是 selection 还是 window 事件） |
| 浏览器正文 | 能 |
| 系统 / 第三方文本控件 | 能 |
| 图片里的字（相册、截图） | 能（信号来自长按，取字靠 OCR） |
| 游戏 / 自绘 UI | **不能**（长按不发任何无障碍事件） |

### 兜底入口（不能删）

| 入口 | 用途 |
|---|---|
| 悬浮球长按 | 游戏、自绘 UI、任何不发信号的地方 |
| 通知栏磁贴 | 不想看到悬浮球时 |

### 第 0 期必须验的四件事

1. 微信长按一条消息 → 有没有 `TYPE_VIEW_TEXT_SELECTION_CHANGED`？
2. 微信长按一条消息 → 有没有 `TYPE_WINDOW_STATE_CHANGED`（新窗口）？
3. 浏览器长按正文 → 有没有 selection 事件？
4. 从"系统菜单出现"到"我们的遮罩盖住"，实测多少毫秒？

**第 4 项超过 100ms 就要改方案**（改成"先黑屏再取字"或者接受菜单露出）。

## 二点五、组件拆解（2026-11-14 定稿，含实测确认）

大爆炸 = 四个独立组件，分开施工、分开验收：

| # | 组件 | 内容 | 档期 |
|---|------|------|------|
| C1 | **词块面板** | 底部圆角面板 + 头部 + 词块网格 + 划选 + ✕ 取消 + 收招 | **v0 核心** |
| C2 | **取字引擎** | 无障碍节点树（v0）→ 截图 OCR 词级（v1） | v0 节点树 / v1 OCR |
| C3 | **顶栏动作** | 复制 · 搜索 · 词典 · 切开 · 分享（5 圆钮） | 复制/搜索/切开/分享 v0；词典占位 |
| C4 | **结果面板** | 动作后的独立弹层：搜索浮窗→全局搜索、词典面板（蓝条+词条列表）、翻译面板 | **v1.5**（C1–C3 落稳之后单独做） |

**C4 实测记录**（R2 + 用户口述）：点搜索/词典后弹**独立结果面板**（底部面板形态，
词典 = 蓝色加载条 + 词条列表；搜索 = 应用内浮窗可跳全局搜索）。这是大爆炸体验的
第二幕，体量不小，**单独拆期**，不塞进 v0/v1 主线。

**v0 范围重申**：C1 全部 + C2 节点树 + C3 四钮 + 触发（信号启发式 + 磁贴 + 调试广播）。
悬浮球 v0 后补。

## 三、取字：两条路，先易后难

### v0 · 无障碍节点树（不截图）

```
AccessibilityService.rootInActiveWindow
  → BFS 遍历
  → 收集 node.text / node.contentDescription
  → 每块带 getBoundsInScreen(Rect)
```

| 优点 | 缺点 |
|------|------|
| 零延迟（< 50ms） | 只能拿"可访问文字" |
| 零误差（就是原文） | 图片里的字拿不到 |
| 不需要截屏权限 | 游戏/自绘 UI/部分 Flutter 页面是空的 |

**粒度 = 控件级**：微信里一条消息一块、浏览器里一段一块。
这已经是可用的产品，但不是原版的"逐词炸开"。

### v1 · 截屏 + OCR（词级）

```
takeScreenshot() → Bitmap
  → OCR（RapidOCR / PaddleOCR-ncnn）
  → 每个字/词带 bounding box
  → 行聚类（y 轴相近的归一行）
  → 行内按标点/空格切
  → jieba 词级细分
```

**粒度 = 词级**，和原版一致。

### 混合策略（最终形态）

```
1. 先读节点树
2. 节点树拿到的文字面积 ≥ 屏幕的 15% → 直接用
3. 否则截图 OCR
4. OCR 失败 → 回退节点树结果，不报错
```

## 四、词块层（悬浮窗）

```kotlin
// 关键：用无障碍自带的窗口类型，不需要额外悬浮窗权限
WindowManager.LayoutParams(
    MATCH_PARENT, MATCH_PARENT,
    TYPE_ACCESSIBILITY_OVERLAY,   // 不是 TYPE_APPLICATION_OVERLAY
    FLAG_NOT_FOCUSABLE or FLAG_LAYOUT_IN_SCREEN,
    PixelFormat.TRANSLUCENT
)
```

**为什么不用 `TYPE_APPLICATION_OVERLAY`**：
- 需要单独申请悬浮窗权限（多一道门）
- 会被系统裁切、可能被输入法顶掉
- 无障碍层跟随无障碍服务生命周期，系统不裁

**坐标对齐**：`getBoundsInScreen()` 是屏幕坐标，悬浮层全屏铺满（含状态栏/导航栏区域），
所以要用 `FLAG_LAYOUT_IN_SCREEN`，并自己处理 inset。

### 选择态（划选后出现）

- 选中词块整体变蓝（含标点块），选区外行不变
- **5 个深色圆形浮钮横排浮现**：搜索 · 词典 · **切开(✂)**（左）｜分享 · 复制（右）
- 选区下方居中一个深色 **✕** 圆钮 = 取消选择（行内嵌，不占顶栏）
- 选中行背后有浅色衬底（圆角矩形，对应官方 select rect）

**关键规则：选中时词块位置一律不动。** 官方 `BoomActionHandler.moveChipRows()` 只对**行**做
`translationY`（上移 −30dp / 下移 +18dp，200ms），行内词块从不重新排布；
操作按钮是浮在 `mBoomTable` 之上的绝对定位层。所以「选中后字突然换位置」在原版不会发生。
我们的实现同理：工具栏在布局里占固定一格，未选中时透明不可点，选中只改透明度。

**词块区自己滚，不铺满全屏。** 官方 `CustomScrollView` 夹在顶栏和底栏之间，
左右留白 `page_margin_left` 17dp / `page_margin_right` 16dp，上下 `content_padding` 35dp。
长文在区域内上下滑，四周留空。

**炸开只做前面若干行。** 官方 `animationRows = min(rowCount, 12)`，只有前 12 行有飞入动画，
后面的行直接就位。整屏 385 个词块同时从按压点飞出会糊成一团。

### 动效时长（逐帧实测）

| 项 | 实测值 | 与官方 2016 版对照 |
|----|----|------|
| 页面切入 | ~200ms 淡入 | ✓ BoomActivity BOOM_DURATION=200 一致 |
| 词块分批入场 | ~300–400ms 全部就位（逐行 stagger，scale 0→1 弹出） | 官方 chip 动画 200ms/块 + 交错 |
| 收招·第一步 | 点空白 → **头部操作钮先消失** | — |
| 收招·第二步 | **~50–100ms 后整页硬切回原 App** | ✗ 老 repo/本文档原估"180ms 词块飞回"**实测不存在** |
| 长按触发阈值 | 录屏中用户按 ~800ms 才出（含反应时间） | 原版系统阈值 ~400ms（无法从录屏反推，沿用） |

> **收招的启示**：OS 8 不做"词块飞回"，直接整页退场——省一段动画，退场更干脆。
> 我们 v0 先做"整页淡出 150ms"对齐实测手感，"词块飞回"作为可选动效开关。
> （老 repo 的 `double_boom_activity_exit`=300ms 下滑出场，仅双指炸路径使用。）

### 进入时的圆圈（官方 BoomOcrActivity 实测参数）

原版炸图路径入场是一枚蓝色圆环，**圆心在按压点**，底下仍是原来的界面：
**从 2f 收到 0.2f**（400ms，透明度 0.4→1）→ **弹回 1.15f**（200ms）。识别还没完成时才在
1.15↔1.10 之间呼吸等待；字已经拿到就**立刻涨到 4f 并淡出**（100ms），同时词块从这一点飞出。
只炸一次。词块先铺满再转圈、转完再炸一次，是错的。

对应资源：`boom_loop.png`（蓝圆）+ `boom_light.png`（旋转光弧），都取自官方仓库
`res/drawable-xxhdpi/`，已复制进本项目 `drawable-xxhdpi/`。

### 交互语义（SwipeSelectView + BoomActionHandler）

- **点空白 = 先清选中，再点才退出。** 官方 `handleClick()`：有选中先清空并返回 true；
  没选中才 `finish()`。我们的实现：空白处轻点，有选中就清空，没有才关面板。
- **从已选中的词块起滑 = 取消这一段。** 官方在 `ACTION_DOWN` 记录 `mIsSelected = !chip.isSelected()`，
  滑过的区间按这个反向状态套用（`performSelect`）：区间内取消、区间外恢复。
- **从空白滑进词块**才开始选中。
- 选中态工具栏是**浮层**，不参与布局，所以选东西时字不会跳。

**触摸分发（R3 修正）**：`BangPanelView` 只在旁边观察「点空白」，不再吃掉触摸。
划选由词块容器 `ChipHost`（对应官方 `SwipeSelectView`）在自己的 `onTouchEvent` 里处理，
滚动由外层 `ScrollView`（对应官方 `CustomScrollView`）负责——两者分层，滚动和划选才能同时成立。
从词块起手做竖向拖动仍然滚动：只有拖到**另一个词块**才 `requestDisallowInterceptTouchEvent(true)`
转入划选；被滚动器抢走时（`ACTION_CANCEL`）撤回「按下即选中」的那一下。
拖到上下边缘时自己滚，对应官方 `scrollIfNeeded`。

**踩过的坑**：早期版本在整个面板的 `dispatchTouchEvent` 里对所有 `ACTION_DOWN` 返回 true，
子视图收不到事件，导致底部 ✕ 关不掉、词块区完全滚不动。触摸不要在上层一律吃掉。

### 分段是「追加」，不是「切换」

官方 `bottom_warning` / `top_warning` 文案（从 APK 解出）：
`「下拉爆炸上一段内容」`、`「上拉爆炸下一段内容」`，拉到位后变成 `「松手爆炸上一段内容」`、
`「松手爆炸下一段内容」`。

录屏逐帧确认：追加后**字数统计会变大**（98 字 → 190 字），已炸出的词块全部保留，
新段落接在末尾（往下一段）或插在最前（往上一段）。不是替换当前这一段。

## 六、状态机

```
Idle
  └─ 长按 ≥400ms ──→ Arming（前摇）
                        └─ 取字成功 ──→ Ready（词块可操作）
                        └─ 取字失败 ──→ Idle（无声退出，不弹错）
Ready
  ├─ 点击词块 ──→ 选中/取消
  ├─ 顶栏操作 ──→ 复制/搜索/分享/存到一步
  └─ 点空白 / 返回键 ──→ Closing（收招）──→ Idle
```

**原则**：任何失败都**静默回到 Idle**，不弹 Toast、不弹对话框。
炸词失败时用户应该觉得"没触发"，而不是"报错了"。

## 七、数据结构

```kotlin
data class WordBlock(
    val id: Int,
    val text: String,
    val bounds: Rect,        // 屏幕坐标
    val source: Source,      // NODE / OCR
    val lineIndex: Int,      // OCR 才有意义
    val groupIndex: Int,     // 同一段落的归组
    val granular: Granularity // WORD / CHAR（切开后的字级块）
)

enum class Source { NODE, OCR }
enum class Granularity { WORD, CHAR }
```

「切开」逻辑：选中块的文本 → 按字符逐个拆块（保留原 bounds 按字符宽度线性切分），
再点一次或在空白处收招后恢复词级。官方 `second_boom`（逐字分词）即此行为。

## 八、边界情况

| 情况 | 处理 |
|------|------|
| 输入法弹出 | 取字时忽略 IME 窗口（`rootInActiveWindow` 只取当前 app 的窗口） |
| 分屏 | 只炸"活动窗口"，不炸两个 |
| 横屏 | 坐标不翻转，`getBoundsInScreen` 已经是屏幕坐标 |
| 视频全屏 | 节点树通常为空 → v1 用 OCR；v0 直接失败退出 |
| 节点数 > 500 | 截断，只取屏幕内可见节点 |
| 微信/QQ 的 WebView | 节点树可能有文字，也可能只有"一个 WebView 节点"，实测记录 |
| 系统弹窗（权限框） | 不炸，直接退出 |

## 十、施工顺序（给执行）

```
1. 工程骨架 + 无障碍服务声明 + 引导页
2. 长按信号捕获（selection / window 事件）+ 遮罩抢先
3. 悬浮球（可拖动、可贴边、长按 400ms）—— 兜底入口
```
