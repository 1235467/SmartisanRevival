# 01 · 权限与门槛

> 这一层决定项目生死。功能做得再好，权限拿不到就是零。
> 本文档所有"Flyme 具体菜单路径"都以**第 0 期真机实测截图**为准，不要凭记忆写死。

---

## 一、权限清单

| 权限 | 给谁用 | 申请方式 | 魅族/Flyme 坑 |
|------|--------|---------|--------------|
| `BIND_ACCESSIBILITY_SERVICE` | 触发层、大爆炸、一步 | 设置里手动开 | **Android 13+ 侧载 App 默认禁止**，要先去"允许受限设置" |
| `SYSTEM_ALERT_WINDOW` | 悬浮球、侧栏、热区 | `ACTION_MANAGE_OVERLAY_PERMISSION` 跳转 | Flyme 有独立的"悬浮窗"开关，和系统权限是两道门 |
| `RECORD_AUDIO` | 闪念胶囊 | 运行时申请 | 后台录音要前台服务 + `microphone` 类型 |
| `POST_NOTIFICATIONS` | 常驻通知、胶囊提醒 | 运行时申请（API 33+） | — |
| `QUERY_ALL_PACKAGES` | 一步/无限屏列应用 | Manifest 声明 | 国行无所谓；上 Google Play 要申报用途 |
| `READ_CONTACTS` | 一步的联系人 | 运行时申请 | — |
| `READ_MEDIA_IMAGES` / `VIDEO` / `AUDIO` | 一步的最近文件 | 运行时申请（API 33+） | Android 14 有"部分照片"新模型 |
| `FOREGROUND_SERVICE` + 类型 | 录音、OCR、保活 | Manifest + 运行时 | **Android 14 必须声明类型**，否则崩 |
| `PACKAGE_USAGE_STATS` | 无限屏的最近使用排序 | 设置里手动开（`ACTION_USAGE_ACCESS_SETTINGS`） | 属于"特殊权限"，容易被忽略 |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | 保活 | 跳转设置 | Flyme 还有自己的一套省电策略，光这个不够 |

## 二、三个"隐形门"

### 门 1：Android 13+ 的受限设置

> **✅ Flyme 实测已过（2026-11-14，魅族 21 Pro / Flyme 12.6.0.0A / Android 16）：无此拦截。**
> 侧载 App 开无障碍时弹的是标准「允许完全控制设备」确认框，直接允许即可。
> Flyme 的应用信息页甚至没有右上角 ⋮ 菜单——它压根没做这道门。

**实测可用路径（截图存 `references/recordings/`）：**

```
设置 → 辅助功能 → 无障碍 → 已下载的应用 → 锤子体检探针 → 使用开关 → 允许
```

**Flyme 两个导航坑（实测）：**
1. `ACTION_ACCESSIBILITY_SETTINGS` 打开的是 Flyme 自家「辅助功能」页，
   标准无障碍服务列表藏在二级页：辅助功能 → 无障碍
2. 原生页组件 `com.android.settings/.Settings$AccessibilitySettingsActivity`
   在 Flyme 上被改名（`MzSettingsActivity$FlymeAccessibilitySettingsActivity`），
   组件直启会落到设置主页

**通用 ROM 仍可能拦截**（原生 Android 13+ 行为：弹"出于安全考虑，此设置当前不可用"），
引导页保留「允许受限设置」兜底文案：
`设置 → 应用 → 本 App → 右上角 ⋮ → 允许受限设置`

**这是首次启动引导里最容易被跳过、也最容易导致"功能全是灰的"的一步。**

### 门 2：Flyme 的悬浮窗是两道门

- 系统权限：`Settings.canDrawOverlays()`
- Flyme 自己的"悬浮窗"开关：在应用权限详情里

两道都开才行。检测方式：试着 `WindowManager.addView()`，捕获 `BadTokenException`。

### 门 3：后台保活

Flyme 的省电策略会杀无障碍服务，表现是"用着好好的，第二天全失效"。

需要同时设置：
1. 应用信息 → 耗电管理 → 允许后台高耗电
2. 应用信息 → 自启动
3. 多任务卡片 → 下拉锁定
4. （可选）`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`

**做不了"技术性保活"，只能做"引导 + 自检 + 失效提醒"。**
不要写相互唤醒、双进程守护那套——现在的 ROM 都能识别，反而会被拉黑。

## 三、截屏权限（大爆炸的命门）

> **✅ Flyme 实测已过（2026-11-14）：`takeScreenshot()` 放行。**
> 魅族 21 Pro：14–29ms 出全分辨率 1368x3192 截图，608ms 间隔连拍无限制报错。
> 基线对比：坚果 R2（Android 11）16ms。决策点 #2 提前通过。

```kotlin
// 1. res/xml/accessibility_service_config.xml
android:canTakeScreenshot="true"

// 2. 代码
takeScreenshot(Display.DEFAULT_DISPLAY, mainExecutor,
    object : TakeScreenshotCallback {
        override fun onSuccess(result: ScreenshotResult) {
            val bitmap = Bitmap.wrapHardwareBuffer(result.hardwareBuffer, result.colorSpace)
            // 用完必须 close
            result.hardwareBuffer.close()
        }
        override fun onFailure(errorCode: Int) { /* 降级到节点树 */ }
    })
```

要点：
- API 30 (Android 11) 起可用
- **有频率限制**（实测约 300–1000ms 一次），一次触发截一帧够用
- 返回的是 `HardwareBuffer`，转 Bitmap 后要尽快 `close()`，否则显存泄漏
- 部分 ROM 会返回 `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT` 或直接禁用

**降级链**：截图失败 → 只读无障碍节点树 → 只支持"可访问文本"，放弃图片内容。

## 四、悬浮窗类型怎么选

| 类型 | 需要权限 | 特点 |
|------|---------|------|
| `TYPE_APPLICATION_OVERLAY` | `SYSTEM_ALERT_WINDOW` | 通用，但会被系统裁切、可能被输入法顶掉 |
| `TYPE_ACCESSIBILITY_OVERLAY` | 只要无障碍服务在跑 | **推荐**。跟随无障碍服务生命周期，系统不裁，不和输入法打架 |
| `TYPE_APPLICATION_ATTACHED_DIALOG` | 附着在某个窗口 | 不适合全局 |

**结论：能挂在无障碍服务上的层，一律用 `TYPE_ACCESSIBILITY_OVERLAY`。**
只有"无障碍没开也要显示"的东西（比如引导浮层）才用 `TYPE_APPLICATION_OVERLAY`。

## 五、首次启动引导（五步）

做成拟物"开箱"流程，每步一个状态灯：

```
1. 欢迎           "把锤子装回来"（一段拟物开箱动画）
2. 无障碍         [开] → 跳系统设置 → 回来检测
3. 悬浮窗         [开] → 跳系统设置 → 回来检测
4. 后台保活       图文引导（4 个子项，逐项打勾）
5. 自检           跑一遍：截屏 → OCR → 显示识别结果
                  "你的手机能炸词" / "只能炸一部分"
```

第 5 步很关键：**让用户当场看到能力边界**，而不是用了一周才发现某功能是灰的。

之后每次启动做一次"体检"：无障碍还活着吗？悬浮窗还在吗？失效就顶部挂一条提醒。

## 六、上架合规（如果以后想发布）

- 无障碍服务：Google Play 要求 `isAccessibilityTool=false` 时填写详细用途说明，审核极严
- 国内商店：无障碍 + 悬浮窗 + 读应用列表，三件套基本会被人工审核
- 只自己用/小范围分发（APK 直装）则无此问题

**当前定位：自用 + 开源。不做商店上架设计。**
